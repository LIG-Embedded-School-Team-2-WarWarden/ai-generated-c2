# FCS / RDR 장애 진단 로그

## ECS에서 자동 기록하는 정보

`--event-log logs/events.log` 실행 시 같은 폴더에 `events.devices.jsonl`을 생성한다.
기본 실행과 Visual Studio F5도 동일하다. JSON 한 줄이 하나의 사건이다.
현재 파일 64 MiB + 과거 `.1`(최근), `.2`, `.3`까지 순환 보관한다.
기존 events.log 보존 정책은 변경하지 않는다. 장애 직후 두 종류 파일을 함께 복사한다.
동시에 여러 ECS를 실행한다면 각 실행에 서로 다른 `--event-log` 경로를 지정한다.

공통 필드: schema, 실행 식별자 run(시작시각/PID), unix_us(UTC epoch), mono_us(실행 내 경과 시간),
source, event, dropped_total(큐 초과/직렬화 실패 누계). 서로 다른 실행의 mono_us를 직접 비교하지 않는다.
8192행 큐와 별도 파일 쓰기 스레드를 사용한다. 파일 오류는 stderr에 알리고 진단을 중지한다.
과부하 시 로그가 유실될 수 있고, 강제 종료/전원 차단 시 큐의 마지막 기록이 남지 않을 수 있다.
로그가 없다는 사실만으로 장치가 패킷을 보내지 않았다고 단정하지 않는다.

| 구간 | 기록 |
| --- | --- |
| 시작 | 실행 파일·빌드 날짜·PID·네트워크 주소/포트·FCS 응답 제한·필터 설정 |
| UDP 송수신 | 실제 바인딩 주소/포트, 상대 주소/포트, 길이, hex 원문, 메시지 ID, TxSeq, ReplyTo |
| 소켓 오류 | 송신 실패 패킷, Winsock 오류 번호, 수신 오류, 수신 핸들러 예외 |
| FCS 요청 | 명령, 순번, 고각/방위각 원시값, 출력 요청값, 응답 제한 |
| FCS 응답 | 수락/폐기, 결과·flags·실측각·출력 상태의 프로토콜 필드, 응답 시간, missed_status, 연결 여부 |
| FCS 폐기 이유 | 상대 주소 불일치, 길이/패딩/필드 오류, 대기 요청 없음, 중복, 기한 초과, 메시지/순번 불일치 |
| RDR 상태 | 매 수락 상태의 원본 flags, 모드·보고·지원·상태 유효·실제 ON·억제, 원본 메시지/순번, 세션/세대 |
| RDR 명령 | 원문 송신(동일 순번 재송신 포함), 매 응답 결과와 경과 시간, 로컬 타임아웃 |
| RDR 폐기 이유 | 세션/순번 불일치, 오래된 상태, 길이/패딩/결과 오류, 객체 상태·좌표 오류, 제외/용량 제한, ED07 모순 |
| ECS 판단 | 기존 이벤트와 할당 상세/차단 사유를 동일 JSONL에 함께 기록 |

정상 ICD 패킷은 전부 저장한다. 비정상 대형 UDP는 앞 4096바이트만 저장하며 length/truncated로 구분한다.
Tx 기록은 운영체제가 송신을 수락했다는 뜻이고 장치 도착 증거가 아니다. Rx 원문은 파서 검사 전 기록이다.
FCS 응답의 result/flags/각도/laser_state는 메시지별 해당 필드만 의미가 있다. 예: FE02의 result 기본값을 명령 성공으로 해석하지 않는다.
DE03의 XYZ·관측각·Detected·TrackState는 원문에 포함된다. RDR 세션 ID는 DE03에 없으므로 인접 제어 흐름과 ReplyTo로 연결한다.
새 연결의 세션 변경, 순번 wrap-around, 재송신을 구분한다. 순번만으로 전체 파일을 join하지 않는다.

## RDR 장비 내부에 반드시 필요한 로그

ECS에는 장치 내부 SDK/하드웨어 상태가 없으므로 아래는 RDR 프로그램에서 별도로 구현해야 한다.

1. 기동: boot_id, 펌웨어 Git commit/build, 보드/센서 모델·시리얼, SDK 버전, 설정값, 재부팅 원인, uptime, 시간 동기화 상태.
2. UDP: 수신·송신 시각/상대 주소/원문, session/TxSeq/ReplyTo, 파서 검증·중복 캐시 적중, 명령 수락/거절 이유, 응답 생성 경로(DE02/DE07 등).
3. ED06/ED07: 요청 모드·억제값, 이전/목표/현재 상태, 접수/장치 호출/완료 각 시각, SDK 함수명·인수·반환 코드·오류 문자열, 재시도·타임아웃·취소 이유.
4. 실제 라이다 상태: supported, known, on, inhibited 각각의 이전값/새값, 변경 원인, 상태 조회 API 결과, 마지막 성공 조회 시각, 상태 나이(ms), 유효기간(ms), 확인 근거(하드웨어 피드백/SDK readback 등).
5. **known=false 사유 코드**: not_initialized / query_timeout / sdk_error / stale_feedback / sensor_disconnected / unsupported_query / transition_in_progress 등 실제 원인별 구분. 원본 오류 코드도 보존.
6. **응답 직전 상태 스냅샷**: 내부 상태 버전, 스레드/작업 ID, raw_flags(hex), 비트별 해석, 상태 근거 시각. DE07 성공 후 DE02에서 known이 내려간 경로를 추적할 수 있어야 한다.
7. 취득: 마지막 센서 프레임 시각·프레임 번호, 수신/유실 수, 센서 연결/재연결, 취득 중 여부. 객체 보고 활성과 실제 방출 상태는 분리한다.
8. 추적: 객체 ID 생성/삭제/재사용, OBSERVED/PREDICTED/LOST 전환 이유, 마지막 실측 시각, XYZ·관측 PAN/TILT, 좌표계/단위, 필터/추적 설정 버전.

요청값이나 DE07 성공 결과를 실제 상태 조회값 대신 사용하지 않는다. `known=false`면 `on=false`를 실제 OFF 확인으로 설명하지 않는다.

## FCS 장비 내부에 반드시 필요한 로그

1. RDR과 동일한 boot_id/build/설정/시간 정보, UDP 원문·순번·세션에 해당하는 연결 정보·중복 처리.
2. EF01~EF05 수신→검증→접수→작업 시작→완료→응답 송신 시각. 접수 ACK와 물리 동작 완료를 별도 사건으로 기록.
3. 거절 사유: busy / 미초기화 / 잘못된 값 / 드라이버 오류 등 내부 세부 사유와 실제 프로토콜 결과 코드를 함께 기록.
4. PAN/TILT: 요청각·변환 후 모터값·실측각·오차·도달 허용치·이동 시작/종료·축별 오류·limit/home/encoder 상태·마지막 실측 시각.
5. FE02 flags: 이전/새 raw_flags, 비트별 상태, 변경 사유, 실제 상태의 출처와 나이. 모터 이동/촬영 중에도 상태 조회 처리 지연을 기록.
6. 표시 레이저/촬영: 요청 ON/OFF와 실제 피드백, 켜짐/꺼짐/촬영 완료 시각, OFF 명령 수신 후 처리 시간, 자동 종료/취소 이유, GPIO/드라이버 호출 결과.
7. 통신/작업 큐: 큐 길이, 요청 대기 시간, 가장 오래 대기한 요청, 루프 최대 정지 시간, UDP 송신 실패, watchdog/예외. 특히 EF02 응답 지연 시 어떤 작업이 실행 중이었는지 기록.

## 장애 수집과 분석 순서

운영자가 버튼을 누른 시각, 객체 ID, 기대 동작, 실제 증상을 함께 남긴다.
ECS events.log + devices.jsonl 및 순환 파일, FCS/RDR 같은 시간대 로그, 각 장비의 build/config를 수집한다.
UTC 시각과 각 장비 monotonic 시각을 모두 기록하고 NTP 오차를 보존한다. 시간 동기화가 없으면 순번·원문 매칭으로 비교한다.
ECS Tx→장비 Rx→장비 판단/하드웨어→장비 Tx→ECS Rx→ECS 수락/거절→GUI 결과 순으로 확인한다.
장비 로그의 상태 스냅샷을 같은 응답의 raw_flags와 비교하면 장비 내부 조회 문제와 비트 조립 문제를 구분할 수 있다.

예: flags=0x020F이면 ACTIVE/보고 ON/지원이지만 bit 4·5가 0이다. 이 경우 RDR의 known 변경 이유와 DE02 응답 생성 직전 스냅샷이 핵심 증거다.
