RDR–ECS 인터페이스 제어 문서 — 제어 24byte·DE03 32byte 개정안

작성일: 2026년 11월 4일
개정일: November 13, 2026
기준: 제공된 RDR·통제소 코드의 rdr-ecs-v07-local1 구현을 바탕으로 좌표 float32·m 및 DE03 32byte 변경 반영

기존 v0.7의 미확정 항목 중 코드에 구현된 내용을 반영하고, 좌표 자료형·단위 및 DE03 길이를 개정했습니다. 제어 메시지는 24byte, DE03 대상 정보는 32byte이며, 필드 배치는 서로 다릅니다. 모든 메시지 길이는 4byte의 배수입니다. 본 문서는 기존 구현을 바탕으로 한 ICD 개정안이며, 변경된 규격의 실제 송수신 코드 반영 여부는 별도 확인이 필요합니다.

1. 통신 규격

항목

정의

통신 방식

UDP

ECS 주소

192.168.0.102:1000

RDR 주소

192.168.0.101:1000

메시지 길이

제어 메시지 24byte, DE03 대상 정보 32byte — 모두 4byte의 배수

바이트 순서

Big-endian

메시지 ID

uint16 숫자 코드

일반 필드

별도 표기가 없으면 uint16

좌표·각도

좌표: float32(IEEE 754 binary32), 4byte, m / 각도: int16, 2byte, 0.1°

세션 ID

uint32, 상위 2byte → 하위 2byte 순서

예약·패딩

길이 범위

24byte·32byte는 애플리케이션 데이터 길이이며 네트워크 헤더 제외

위 주소는 팀 네트워크 직접 통신 설정입니다. ECS와 RDR 실행 설정에도 상대 주소를 동일하게 적용해야 합니다.

예를 들어 ED01은 문자열 "ED01"이 아니라 ED 01 두 바이트로 전송합니다.

2. 전송 데이터

  1. Target ID

  2. 원본 센서 X/Y/Z 좌표 — float32, 단위 m. PAN/TILT 회전 보정 전

  3. 모터 고각·방위각 — 단위 0.1°

  4. 대상별 감지 여부 — Detected

  5. 모터 움직임 관측 상태 — MotorRunning

  6. 연결·감시·전체 보고 상태

  7. 전체 보고 허용·중지 및 대상별 보고 제외·재개 명령

  8. 감시 시작·정지 명령과 적용 결과

동시에 보고 슬롯에서 관리하는 대상은 최대 10개입니다. 대상 1개당 DE03 32byte 패킷을 각각 전송합니다.

전체 포인트 클라우드와 TXT 추출은 별도 인터페이스입니다.

3. 메시지

[ED01] 1. 연결 요청 ECS → RDR

  • 최초 연결 또는 연결 만료 후 재연결에 사용합니다.

  • ECS가 0이 아닌 세션 ID를 생성하여 전송합니다.

  • 연결 요청만으로 감시를 시작하지 않습니다.

[DE01] 2. 연결 요청에 대한 응답 RDR → ECS

  • 연결 적용 결과와 현재 상태를 응답합니다.

  • 새 연결에서는 전체 보고를 중지하고 대상 ID·보고 제외 목록을 초기화합니다.

  • 기존 연결 중 다른 세션 ID로 연결을 요청하면 BUSY를 응답합니다.

[ED02] 3. 1초 주기로 상태 확인 요청 ECS → RDR

[DE02] 4. 현재 상태 응답 RDR → ECS

보내는 정보:

  • 모터 움직임 관측 상태

  • 현재 모터 고각·방위각

  • 연결 여부

  • 감시 활성 여부

  • 전체 보고 허용 여부

  • 감시 운용 모드

DE02에는 Detected 필드가 없습니다. 대상별 감지 여부는 DE03으로 전송합니다.

[ED03] 5. 전체 대상 보고 허용·중지 ECS → RDR

  • 0: 보고 중지

  • 1: 보고 허용

  • 외부 대상 송신만 제어하며 감지·추적·회전을 정지하지 않습니다.

  • 별도 확인 응답은 없습니다.

  • 적용 여부는 DE02의 전체 보고 허용 플래그로 확인합니다.

[DE03] 6. 대상 정보 RDR → ECS

  • 연결 완료·감시 ACTIVE·전체 보고 허용 상태에서 전송합니다.

  • 보고 제외된 Target ID는 송신하지 않습니다.

  • 약 1초 간격의 보고 처리에서 대상별 패킷을 전송합니다.

  • DE03은 ED03에 대한 확인 응답이 아닙니다.

[ED04] 7. 대상별 보고 제외·재개 요청 ECS → RDR

  • Target ID와 보고 허용 상태를 지정합니다.

  • 0: 지정 ID 보고 제외

  • 1: 지정 ID 보고 재개

  • 해당 대상의 내부 검출·추적과 다른 대상의 보고는 유지합니다.

[DE04] 8. 대상별 보고 제어 응답 RDR → ECS

  • 대상 Target ID, 요청한 보고 허용 상태, 적용 결과를 응답합니다.

  • RDR이 알고 있지 않은 ID이면 UNKNOWN_ID를 응답합니다.

[ED06] 9. 감시 시작·정지 요청 ECS → RDR

  • 0: 감시 정지

  • 1: 감시 시작

  • 감시 시작 시 센서 취득과 방위각 왕복 탐색을 실행합니다.

  • 고각은 시작 위치를 유지합니다.

  • 감시 정지는 원점 복귀나 전원 차단 명령이 아닙니다.

[DE06] 10. 감시 시작·정지 적용 결과 응답 RDR → ECS

  • PENDING: 시작·정지 처리 중

  • OK: 시작 조건 또는 정상 정리 완료 확인

  • FAILED: 처리 실패

  • 한 요청에 대해 PENDING과 최종 결과가 순차적으로 전송될 수 있습니다.

  • 전체 영역의 탐색 1회 완료를 의미하지 않습니다.

[ED07] 11. 라이다 방출 정지·재개 요청 ECS → RDR

  • 0: 라이다 방출 억제 설정 및 실제 방출 정지

  • 1: 방출 억제 해제. 감시 ACTIVE일 때 방출 재개하며, IDLE에서는 OFF 유지

  • 보고 중지(ED03)·감시 정지(ED06)와 별도이며 모터·전체 보고 설정을 변경하지 않습니다.

[DE07] 12. 라이다 방출 제어 적용 결과 RDR → ECS

  • 요청값·세션·대응 Sequence·처리 결과와 현재 상태 플래그를 응답합니다.

  • PENDING은 요청 접수·처리 중입니다. OK는 이번 요청에 대응하는 SDK START/STOP 명령의 정상 처리와 RDR 내부 제어 전환 완료를 뜻합니다. 실제 방출 ON/OFF 확인은 bit 4·5로 별도 보고하며 DE07 OK만으로 보장하지 않습니다.

6.2 제어값·감지·모터 상태

필드

값 정의

보고 허용 상태 — ED03

0: 전체 보고 중지, 1: 전체 보고 허용

보고 허용 상태 — ED04

0: 지정 ID 보고 제외, 1: 지정 ID 보고 재개

감시 요청 상태 — ED06

0: 감시 정지, 1: 감시 시작

Detected — DE03

0: LOST 또는 PREDICTED, 1: OBSERVED. TrackState와 함께 해석

MotorRunning — DE02

0: 정지 관측, 1: 움직임 관측, 2: 확인 불가

MotorRunning은 UART 위치 표본의 변화로 판단합니다. 두 표본 간격이 0.5초 이하이고, 고각·방위각 중 어느 한 축이라도 위치 차이가 1tick을 초과하면 움직임으로 판단합니다.

위치 정보가 0.5초 넘게 갱신되지 않으면 MotorRunning은 2, 현재 각도는 -32768로 설정합니다. 순간 정지와 감시 종료는 구분합니다.

bit 4는 외부 광학 센서 설치 여부가 아니라 bit 5의 유효성 표시입니다. RDR은 검증된 장치·SDK 상태로 판단합니다. bit 6은 억제 설정이며 실제 OFF 확인과 다릅니다. bit 4=0이면 bit 5=0도 OFF로 해석하지 않습니다.

6.4 좌표·각도

항목

정의

X/Y/Z 단위

m(미터). 예: 1.0 → 1m, 0.001 → 1mm

좌표 표현 범위

float32(IEEE 754 binary32)의 유한값 표현 범위, 단위 m. 운용상 허용 좌표 범위는 별도 정의

각도 단위

0.1°. 예: 100 → 10°
0.1°는 통신 표현 단위이며 모터의 실제 분해능 보장치가 아닙니다.

각도 알 수 없음

-32768

PAN 패킷 기준

북쪽 PAN=1800(180.0°), 오른쪽 회전이 양수

TILT 패킷 기준

수평 TILT=0, 위쪽 회전이 양수

모터 각도 환산

모터 tick 영점·부호·기어비는 RDR 내부에서 보정하여 위 패킷 기준으로 변환. tick 값을 직접 송신하지 않음

송신 좌표계

원본 센서 좌표. 수신 X는 좌우 반전: right=-X, up=Y, forward=Z. ECS에서 관측 PAN/TILT를 한 번만 적용

LOST 패킷 (TrackState=0)

X/Y/Z = 0.0(float32, m), 고각·방위각 = -32768

RDR은 PAN/TILT를 미리 적용한 좌표를 보내지 않습니다. ECS는 관측 자세로 동쪽·북쪽·위쪽 좌표를 계산하고 설치 위치를 더합니다. 센서·모터 축의 장착 회전은 단위행렬, 장착 이동량은 0을 가정하므로 실장비 장착 기하 검증은 별도입니다.

DE03의 각도는 대상의 방위각·고각을 계산한 값이 아니라 관측 당시 모터 각도입니다.

7. 정상 통신 절차

  1. ECS가 새 세션 ID로 ED01을 전송합니다.

  2. RDR이 DE01 OK를 응답합니다.

  3. ECS가 ED02 상태 확인을 1초 주기로 수행합니다.

  4. ECS가 ED03 보고 허용을 전송합니다.

  5. ECS가 DE02의 보고 허용 플래그를 확인합니다.

  6. ECS가 ED06 감시 시작을 전송합니다.

  7. RDR이 DE06 PENDING을 응답하고 기동합니다.

  8. SDK 준비·최신 모터 위치 등 시작 조건이 확보되면 DE06 OK를 응답합니다. 방출 억제 중에는 억제를 유지한 ACTIVE 진입을 허용하고 새 광학 프레임 수신을 시작 완료의 필수 조건으로 요구하지 않습니다. 실제 취득·새 관측은 ED07 재개 완료 후 시작합니다.

  9. RDR이 보고 가능한 대상별 DE03을 전송합니다.

  10. 필요 시 ED04·DE04로 특정 ID 보고를 제외·재개합니다.

  11. ED06 감시 정지 후 DE06 최종 결과로 정지 완료 여부를 확인합니다.

8. 재전송·연결 만료·대상 소실

  • TxSeq는 16bit 순환 번호입니다. 동일 요청 재전송은 원래 TxSeq와 패킷 내용을 유지합니다.

  • RDR은 저장된 동일 요청에 대해 캐시 응답을 반환하며 하드웨어 동작을 반복하지 않습니다. ED03은 별도 응답이 없습니다.

  • 같은 TxSeq에 다른 내용을 사용하면 CONFLICT, 오래된 번호는 STALE로 처리합니다.

  • RDR의 유효 명령 수신이 3.5초를 초과해 끊기면 연결·전체 보고를 해제하고 감시 정지를 요청합니다.

  • 재연결 후에는 명시적인 감시 시작 명령을 다시 받아야 합니다.

  • 통제소 C++ 구현은 마지막 유효 상태 갱신 후 3.2초 초과 시 새 연결을 시도합니다. 별도 Python 시험 패널은 ED02 연속 3회 미응답 기준을 사용합니다.

  • 실제 관측은 TrackState=1/Detected=1, 유효한 예측은 TrackState=2/Detected=0으로 보냅니다. 예측은 마지막 실제 관측 또는 점군 지지 후 최대 1.5초까지만 유효하며 예측 자체로 기한을 연장하지 않습니다. 소실은 TrackState=0/Detected=0, XYZ=0, 관측 각도=-32768로 알립니다. ECS의 마지막 DE03 수신 후 3초 만료는 별도 통신 타임아웃입니다.

  • 대상이 전혀 없으면 별도의 빈 대상 패킷은 보내지 않습니다.

  • 보고 제외된 대상은 Detected=0 패킷도 보내지 않습니다.

  • 새 연결에서는 ID·제외 목록을 초기화합니다. 같은 연결의 감시 정지·재시작에서는 제외 설정을 유지합니다.

DE03에는 세션 식별자가 없으므로 이전 세션에서 지연된 대상 패킷을 완전히 구분할 수 없습니다. 엄격한 대상 데이터 세션 구분이 필요하면 별도 ICD 개정이 필요합니다.

9. RDR 라이다 방출 제어 — SDK 명령 완료와 상태 확인 분리

개정일: November 13, 2026. 비무장 교육·시연 장치의 RDR 라이다와 FCS 레이저 연동 규격입니다.

적용 상태: 이 개정은 DE07 OK의 의미를 변경한 신규 계약입니다. 문서 갱신만으로 ECS·RDR 실행 코드가 변경되는 것은 아닙니다. 기존 ECS는 bit 4=0인 DE07 OK를 거절하므로 양측 구현과 시험을 함께 완료한 뒤 적용해야 합니다. 패킷에 개정 버전 구분 필드가 없으므로 연결된 양측의 배포 버전을 운영 기록으로 관리하고, 구·신 의미를 자동 추측하지 않습니다.

항목

정의

메시지 ID

ED07=0xED07, DE07=0xDE07. 기존 24byte Big-endian 필드 배치 유지

byte 6–7

uint16 lidar_request. 0: 억제 설정·STOP, 1: 억제 해제·ACTIVE에서는 START, IDLE에서는 STOP. DE07은 요청값 복사

byte 8–9

예약=0. DE07도 0

byte 10–13

uint32 세션 ID. 요청 세션을 응답에 복사

byte 14–15

DE07 결과: 0 OK, 1 PENDING, 2 INVALID, 3 NO_SESSION, 4 BUSY, 5 FAILED, 7 STALE, 8 CONFLICT

byte 20–21

상태 플래그. bit 3–6의 의미와 모든 제어 응답에서의 위치 유지

DE07 OK

이번 요청에 대응하는 SDK 명령이 정상 처리됐고 RDR 내부 제어 전환도 완료됨

DE07 PENDING

SDK 응답 또는 내부 제어 전환을 기다리는 중. 완료가 아님

실제 RDR 방출 OFF 확인

bit 3=1, bit 4=1, bit 5=0. FCS 레이저 허용 전에는 억제 설정 bit 6=1 및 대응 DE07 정지 OK도 필요

실제 RDR 방출 ON 확인

bit 3=1, bit 4=1, bit 5=1. 재개 완료 상태에서는 bit 6=0

상태 미확인

bit 4=0. SDK 명령 처리 성공 여부와 독립적이며 bit 5=0을 OFF로 취급하지 않음

RDR 구현 요구사항

  1. ED07=0을 받으면 억제를 설정하고 데이터 진입을 차단한 뒤 SDK STOP을 요청합니다. ED07=1은 ACTIVE에서 SDK START, IDLE에서 SDK STOP을 요청하며 감시·모터를 자동 시작하지 않습니다. 그 밖의 전환 중·오류 모드는 BUSY 또는 FAILED로 처리하고 성공을 추정하지 않습니다.

  2. DE07 OK는 이번 START/STOP 요청에 대응하는 새롭고 유효한 응답, SDK 명령 성공, RDR 내부 제어 전환 완료를 모두 요구합니다. 함수 호출 반환만으로 성공 처리하지 않습니다. TEST 응답이나 오래된 캐시값을 START/STOP 성공 근거로 사용하지 않습니다.

  3. 현재 전달된 RDR의 응답 유효성 기준은 serial 증가, expected command 일치, 유효한 결과 범위, 응답 시각의 나이가 0 이상 0.5초 미만인 것입니다. START/STOP 성공은 SDK ack와 새 응답의 result=0을 모두 요구합니다. TEST 조회의 상태 헤더 사용과 START/STOP 성공 판단은 분리합니다.

  4. 정상 처리된 START/STOP 응답의 장치 상태가 7(WARN_TEMP)이면, 그 이유만으로 명령 처리 완료를 실패시키지 않습니다. 내부 제어 전환까지 완료되면 DE07 OK를 반환하되 bit 4=0, bit 5=0으로 방출 미확인을 유지합니다. 상태 7은 실제 과열 또는 OFF/ON을 확정하는 근거가 아닙니다.

  5. 상태 2(IDLE)는 OFF, 상태 3(STREAM)는 ON으로 대응하는 현재 설치 장치의 검증 프로필을 사용합니다. 새롭고 유효한 응답에서 판정 가능하면 bit 4=1이고, 상태 2는 bit 5=0, 상태 3은 bit 5=1입니다. 응답 노후화·연결 단절·판정 불가에서는 bit 4=0으로 되돌립니다. 이 매핑은 독립적인 광학 측정이 아니며 다른 장치에 무조건 적용하지 않습니다.

  6. 명령 거절, 잘못된 응답, 시간 초과, 연결 끊김은 OK로 처리하지 않습니다. 상태 7 이외의 오류 상태를 일괄 성공 처리하지 않습니다. 새 응답에서 목표 상태와 명백히 반대인 정상 상태가 확인되면 전환을 기다리거나 실패 처리하고 목표 달성을 주장하지 않습니다.

  7. bit 6은 억제 래치입니다. 정지 처리 완료 시 1, 재개 처리 완료 시 0입니다. 억제 상태에서 SDK 재초기화·ED06·재연결로 START를 실행하지 않습니다. 실패 시 억제를 임의로 해제하지 않고 실제 내부 설정을 보고합니다.

  8. SDK 지원 여부와 SDK 명령 성공을 bit 4에 복사하지 않습니다. 지원 여부는 bit 3이며, bit 4는 방출 상태 판정 가능 여부입니다.

  9. 같은 Sequence·동일 내용의 재전송은 같은 요청입니다. 하드웨어 동작을 불필요하게 반복하지 않고 PENDING 캐시를 최종 결과로 갱신합니다. DE07 최종 캐시 응답의 방출 상태가 이후 DE02보다 오래되면 ECS는 최신 상태를 되돌리지 않습니다.

  10. 로그에는 SDK command, ack, reply result, device state, 응답 나이, bit 3–6, DE07 결과를 분리해 남깁니다. 장치 상태 7의 원인은 현재 DE02의 bit 4만으로 ECS에 전달되지 않습니다. 진단 코드 추가 전에는 상세 원인을 RDR 로그로 확인합니다.

ECS 처리 및 FCS 레이저 연동

  1. RDR 제어 응답의 세션·메시지 ID·대응 RxSeq·요청값·결과를 검증합니다. DE07 OK 검증에서 bit 4=1을 필수로 요구하지 않고 SDK 제어 완료와 방출 상태 유효성을 분리합니다.

  2. RDR 단독 감시 준비는 연결·지원·명령 충돌 여부 등을 검사하고, 방출 억제를 유지한 채 bit 4=0이어도 ED06 준비를 진행할 수 있습니다. RDR 미지원이나 연결 단절을 정상으로 바꾸지 않습니다.

  3. GUI의 감시 준비, SDK 제어 명령 완료, RDR 방출 확인/미확인을 구분해 표시합니다. 상태 미확인에서 SDK 제어가 완료되었다는 이유만으로 “실제 방출 ON 확인”을 표시하지 않습니다. 기존 GUI IPC 필드만으로 표현이 부족하면 별도의 호환 가능한 진단 표현을 양측 배포에서 마련합니다.

  4. FCS 레이저 ON 또는 레이저를 사용하는 EF05 전에 RDR ED07=0의 명령 처리 완료와 최신 RDR 방출 OFF(bit 4=1, bit 5=0), 억제(bit 6=1)를 모두 확인합니다. DE07 OK만으로 FCS 레이저 방출을 허용하지 않습니다. bit 4=0이면 FCS 레이저 방출을 차단합니다.

  5. RDR OFF 확인 후 FCS의 최신 연결·무오류·모터 정지·시연 정지·레이저 OFF도 확인한 뒤 FCS 출력 명령을 보냅니다. RDR DE02와 FCS FE02는 서로 다른 장치 상태입니다.

  6. FCS 레이저 종료 또는 명시적 OFF 확인 후 RDR ED07=1을 요청합니다. RDR SDK 명령 완료와 RDR 방출 ON/OFF 확인을 각각 갱신합니다. 타임아웃만으로 방출 상태를 확정하지 않습니다.

  7. RDR ED07 내부 처리 제한은 5초입니다. 이 개정의 ECS ED07 요청 만료·최종 응답 대기 기준은 6초(처리 5초 + 통신 여유 1초)로 맞춥니다. 상위 절차와 하위 재전송 타임아웃을 함께 변경하고 실제 지연을 측정합니다. 타임아웃 후에는 결과 미확정으로 처리하며 뒤늦은 응답이 만료 요청을 부활시키지 않게 합니다.

  8. 연결 세션이 바뀌면 이전 완료 근거를 재사용하지 않습니다. 여러 FCS의 연동은 모든 연결된 출력 장치의 종료 확인이 필요하며 현재 ECS는 FCS 1대 기준입니다.

관련 FCS 메시지: FCS-ECS ICD.

10. ECS 적용 및 장치 간 확인 사항

DE03은 기존 32byte, TrackState 0/1/2, 원본 센서 XYZ 및 관측 PAN/TILT 계약을 유지합니다. 이번 개정은 DE07 완료 의미와 ECS의 준비·상태 판단 분리에 관한 변경입니다.

현재 배포 코드가 이 문서와 같다고 가정하지 않습니다. 기존 ECS의 시작 전 bit 4 차단, DE07 수신 시 bit 4 필수 조건, 최종 구동 판단, 2초 요청 만료, GUI 표시와 테스트를 함께 수정해야 합니다. RDR의 DE07 OK 판단도 같은 개정으로 배포해야 합니다.

GUI RDR 구동에서 FCS가 연결되어 있으면 기존 FCS 레이저 OFF 확인을 수행합니다. FCS 미연결 또는 비활성화 상태에서는 해당 FCS 확인을 생략합니다. 이는 RDR 방출 상태를 확인했다거나 실제 FCS 레이저가 OFF라는 뜻이 아닙니다. 연결된 FCS의 OFF 확인 실패를 성공으로 처리하지 않습니다.

DE06 시작은 억제 중에도 SDK 준비·감시 실행 경로·최신 UART 자세 등의 조건으로 완료할 수 있어야 합니다. 새 광학 프레임이나 방출 ON 확인을 ED06 준비 완료 필수 조건으로 삼지 않습니다. DE06 정지 OK 역시 실제 방출 OFF 확인과 다릅니다.

개정 인수 테스트

  • 상태 2·3·7의 새 SDK 응답에서 ED07 결과와 bit 4·5·6을 각각 검증합니다.

  • TEST 응답 혼입, 오래된 캐시, 잘못된 command, SDK 실패, 연결 끊김, PENDING 및 5초 처리 한도·6초 ECS 만료를 검증합니다.

  • bit 4=0인 억제 상태에서 ED06 준비와 SDK 제어 완료가 가능하되, 방출 상태는 미확인으로 남는지 확인합니다.

  • DE07 정지 OK + bit 4=0에서는 FCS 레이저 출력 요청이 전송되지 않는지 확인합니다.

  • 문서 개정, ECS·RDR 빌드 버전, 모의 시험 및 실제 장치 시험 결과를 각각 기록합니다.

11. 방출 중단 중 객체 ID 보존 및 재관측

개정일: November 13, 2026. ED07에 의한 짧은 방출 중단을 일반적인 객체 소실과 구분합니다. 동일 객체 여부와 ID 연결은 RDR 책임이며 ECS는 새 ID를 옛 ID로 치환하지 않습니다. ED07/DE07 24byte 및 DE03 32byte 배치와 TrackState 0/1/2는 유지합니다.

RDR 담당자 구현 항목

  1. ED07=0 수락 시 기존 추적 ID·마지막 실제 관측 시각·위치·속도·관측 특징을 별도 보관합니다. 광원 정지나 SDK 취득 재시작만으로 추적 ID 할당기를 초기화하지 않습니다. 의도적인 중단 중 미관측 횟수만으로 보관 ID를 삭제하지 않습니다.

  2. 초기 보존 상한은 중단 10초, 재개 후 재획득 대기 3초입니다. RDR은 단조 시계로 중단 수락 및 실제 재개 완료 시점을 기록합니다. 중단이 10초 이상이면 기존 동일성 보관을 폐기하고 새 관측을 새 ID로 처리합니다. 재개 후 3초 안에 대응하지 못한 ID도 폐기합니다. 중복 ED07 재전송으로 기한을 연장하지 않습니다.

  3. 재개 후 실제 관측을 보관 추적 정보와 일대일로 대응시킵니다. 대응이 확실한 경우에만 같은 ID를 유지합니다. 객체 교차·복수 후보·불확실한 이동에서는 억지로 옛 ID를 유지하지 않고 새 ID를 부여합니다. 다른 객체에 폐기된 ID를 같은 세션에서 재사용하지 않습니다. ID 고갈 시 세션을 갱신합니다.

  4. DE07 재개 SDK 명령 처리 OK 이후 실제로 새로 취득한 결과로만 OBSERVED(TrackState=1, Detected=1)를 전송합니다. 정지 전 버퍼·대기 송신 데이터를 폐기하고 새 관측의 자세와 XYZ를 함께 전송합니다. PREDICTED만으로 재획득 완료를 선언하지 않습니다. 기존 예측 유효 한도 1.5초를 늘리지 않습니다.

  5. 중단·재획득 대기 중 새 관측을 만들지 않습니다. 기존 LOST 전송 또는 DE03 송신 공백과 별개로 내부 동일성 보관은 유지할 수 있습니다. 관측 재획득에 성공하면 원래 ID로 OBSERVED를 보내고, 실패하면 LOST 또는 보고 종료로 처리합니다.

  6. 명시적 ED06 정지·보고 중지·연결 세션 변경·재부팅은 이 짧은 중단 연속성의 대상이 아닙니다. 이전 세션 ID를 새 객체와 연결하지 않습니다. ED04 제외된 ID는 복구 표시·재획득 보고 대상에서 제외합니다.

4/5는 ECS–GUI 표시 상태이며 DE03 TrackState에 4/5를 보내지 않습니다. GUI 프레임 v3의 크기·필드 오프셋은 유지합니다. 구형 GUI는 valid=0을 숨기므로 새 표시를 보려면 GUI도 갱신해야 합니다. 보존 좌표로 신규 할당·실행하지 않습니다. 순차 목록은 해당 ID의 재관측을 최대 13초 기다리고 다른 ID로 대체하지 않습니다.

ECS는 중단 요청부터 10초, DE07 재개 SDK 명령 처리 완료부터 3초의 표시 기한을 사용하며 타임아웃은 광원 재개 명령의 근거가 아닙니다. 연결/감시/보고 중지·RDR 설치 위치 변경·세션 변경에서는 표시 보관을 지웁니다. 이전의 실행 정렬 상태를 자동 복원하지 않으므로 필요 시 다시 할당합니다. 표시 보관은 수신 데이터의 기존 3초 유효성 만료를 연장하지 않습니다.

DE03에는 취득 시각이나 중단 세대 필드가 없으므로 ECS의 재개 이후 수신 시각 검사만으로 지연된 이전 프레임을 완전히 식별할 수 없습니다. RDR의 버퍼 폐기·순번 관리·실제 새 관측 송신이 필수입니다. 실장비 재획득 정확도와 동작 시간은 별도로 검증해야 합니다.

장치 인수 테스트

정지 객체의 같은 ID 복원, 여러 객체의 일대일 대응, 교차·대체 객체의 새 ID, 중단 10초 초과와 재획득 3초 초과, 재개 전 예측/지연 프레임, 동일 ED07 재전송, 연결 단절·감시 정지·재부팅을 시험합니다. RDR 펌웨어와 실제 센서를 통한 동일성 검증은 ECS/GUI 모의 시험과 별개입니다.
